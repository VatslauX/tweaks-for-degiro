# Extension architecture

## Execution worlds

The manifest declares two content-script worlds:

- **Isolated world:** `common-isolated.js`, `flags.js`, `content.js`, `exdiv.js`, `compact.js`, `hide.js`, `adjust-close.js`, `ui.js`, `orders-table.js`, `portfolio-table.js`, `alarm-rules.js`, `chime.js`, `alarm-lock.js`, `alarms.js`, `alarm-panel.js`, `alarms-page.js`, `nav.js`, and `status.js`. These can use `chrome.storage`.
- **Page world (`world: "MAIN"`):** `common.js`, `chart-select.js`, `orders.js`, `alarm-lines.js`, `period.js`, and `portfolio.js`. These cannot use `chrome.*` or isolated-world settings globals. Highcharts features act only on `__dgt.mainChart()` (the largest visible chart with a price series).
- Each world has its own TypeScript project. Keep the `files` entries in the matching `tsconfig.*.json` aligned with the manifest; the unit tests check this.

## Shared code and scheduling

`common.js` exposes frozen global `__dgt`; Chrome injects a file only once per page, so `common-isolated.js` is its copy. Edit `common.js`, then run `npm run sync-common`.

- Add DEGIRO selectors, label patterns, and routes to `SEL`, `LABELS`, or `page` in `common.js`, not feature files.
- Features use `feature({ name, enabled, run, stop?, every?, throttle? })`. The scheduler has one MutationObserver and timer per world, runs enabled features at most once per frame, and throttles DOM-driven runs to 150 ms unless configured otherwise. Settings changes bypass throttling. Each world's observer watches the `data-dg-tweaks` and `data-dg-alarm-lines` attributes on `<html>`. Timer-only flushes run features whose `every` interval is due. `stop()` runs once when disabled.
- `run()` must be idempotent, return `ok`, `idle`, or `missing`, and degrade quietly when expected page content is absent. Exceptions are contained per feature.
- Mark inserted elements with `own(el)` (`data-dg-own`) so our DOM changes do not trigger reruns. Avoid render loops and expensive work on every frame.
- Page-world statuses cross to the isolated world in `data-dg-status`; because the page can write it, `status.js` accepts only known feature names and values. Nothing is stored.

## Settings and translations

- `DG_DEFAULTS` in `flags.js` defines the settings stored in `chrome.storage.sync`; `dgSanitize` maps malformed values to defaults, and `dgOnSettings(fn)` runs immediately and on changes. `flags.js` is also loaded by `options.html`.
- Page-world scripts receive settings only in the `data-dg-tweaks` JSON attribute on `<html>`. It must contain only keys listed in `DG_PAGE_FLAGS`, because page scripts can read it. Adding a page-world flag also requires updating `tests/e2e/bridge.spec.js`. Settings apply live without reload.
- A failed `chrome.storage.sync` read keeps the last good settings and retries (1 s, doubling to 30 s); before the first good read, `data-dg-tweaks` is not written, so page-world features stay off.
- If the extension is disabled, removed, or updated, `flags.js` detects that `chrome.runtime.id` is gone (checked every 2 s) and switches all flags off, stopping both worlds.
- Locales live in `_locales/<lang>/messages.json`; `default_locale` is English and the extension name stays English. Visible text uses `__dgt.t(key, ...subs)` or `data-i18n` in `options.html`. Page-world text keys must also be in `PAGE_TEXTS` in `common.js`; page-controlled text is used only as `textContent` or `title`.

## DEGIRO-specific feature notes

- **Orders (`orders.js`):** `sessionId` and `intAccount` are discovered from DEGIRO's own resource requests. Only when none is observed after 5 s, a fallback runs at most once a minute: `/login/secure/config` reads `data.sessionId`; `/pa/secure/client?sessionId=` reads only `data.intAccount`. A 401/403 rejects that session permanently. Retry delay starts at 20 s and doubles to 5 min. Ignore the extension's own request URLs in the session watcher. `portfolio.js` retries failed value requests after 30 s, doubling. Orders poll the same-origin `/trading/secure/v5/update/{acc};jsessionid={sid}?orders=0` every 20 s. Clicking a badge may open DEGIRO's Adjust order form only after uniquely matching its Outstanding order row. A panel toggle with `data-value` other than `opened` means the panel is minimized.
- **Price alarms:** in the tabs, isolated-world DOM reads only, no requests, except one for the opt-in background check (below: product details from DEGIRO). Prices come from Favourites (`LastPrice`) and product page (`CurrentPrice`), and checks run only while one of those is open. `dgAlarms` is synced across the Chrome profile (max 25); `dgAlarmState` and `dgAlarmEvents` are local to the browser. “Every time” arming is tab memory only, reset when another writer's firing changes the stored `firedAt`. A tab keeps its own unsaved state when a storage change lands mid-write: what `check()` handed `record()` (`last`/`lastAt`, and `firedAt` of its firings; after the merge, the firing that won) stays in `pending` and is laid over `state` whenever storage replaces it (`onChanged`, a merge), until that `record()`'s write completes or fails; otherwise an alarm's first firing would fire again on the next check (a second chime). Only alarms still in the tab's list are overlaid; `update()` drops the edited alarm's entry. Likewise a fired 'once' alarm's switch-off (`on: false`, set in the tab at once, stored only at the end of `record()`) stays in `offing` and is laid over every list that replaces `alarms` from storage (`onChanged`, `reload()`, `saveAlarms()`, whose base is the stored list), because `R.decide` fires a reached 'once' alarm whatever its `firedAt` and `foreignWithin` ignores the tab's own; without it another writer's list write, or an earlier `record()`'s switch-off of another alarm, would switch it back on and the next check would fire it again. The entry goes once that `record()` stored the switch-off, or before the tail when its merge dropped the firing (the winner switches it off), and at once on `setOn()`/`update()` of that alarm (the user's choice). If storage refuses the switch-off, the entry stays (otherwise the alarm would fire and chime on every check) until a later list write of the tab stores it, or the user switches the alarm on or edits it in that tab. Cross-tab duplicate suppression uses 60 s, or the same local day for “Once a day”; near-simultaneous tabs can race only when the alarm-data lock is unavailable (below), with one event retained. Banners appear in every DEGIRO tab.
- **Alarm-data lock (`alarm-lock.js` client, keeper in `background.js`):** every read-modify-write of `dgAlarms` (sync), `dgAlarmState` and `dgAlarmEvents` (local) holds one lock, so writes a few ms apart (tabs, the worker, the settings page) can't lose each other's updates; Web Locks can't be shared (the tabs run on DEGIRO's origin).
  - **Keeper:** the service worker, in memory: one holder; waiters in two levels, DEGIRO tabs and the settings page (every message client) before the worker's own write, FIFO within a level; no pre-emption, but a turn lasts at most 5 s (`LOCK_LEASE`). Its listeners are registered whatever the settings, so a tab's write wakes the worker even with the background check off.
  - **Protocol (no `postMessage`):** `dgAlarmLock.hold()` opens `chrome.runtime.connect({ name: 'dg-lock:<crypto.randomUUID()>' })` for liveness only, then sends `{ type: 'dg-lock', token }`; the worker holds the reply (`return true`) and answers `true` on the client's turn. `port.disconnect()` releases; a closed or crashed tab's port disconnects, which frees its turn or drops it from the queue. Port and message may arrive in either order (the lease covers a port that never shows up); a message whose port already went (kept 5 s in `lockGone`) is answered `false`. Both listeners require `sender.id === chrome.runtime.id`; tokens must match `^[\w-]{8,64}$` (the worker's own are `bg:<n>`), others are refused. The holder check is by token, so an expired holder's late disconnect frees nobody else.
  - **Fallback:** no answer in 2 s, `connect`/`sendMessage` throwing (context invalidated, worker restarting), a reply other than `true`, or the port disconnecting while waiting (worker died) → the client disconnects and writes without the lock, as before. The worker goes on without it after 10 s of waiting (`LOCK_WAIT`), so a tick never hangs.
  - **What's wrapped:** in `alarms.js`, `locked(fn)` = `serial(() => dgAlarmLock.run(fn))` (the lock is taken inside the tab's queue item, so the tab's own order is unchanged): `record()` (fresh read, merge, local write, 'once' switch-off), `update()`, `closeEvent()`, `dropOrphans()`, and `saveAlarms(edit)` behind `add`/`setOn`/`remove`, which now shows the change at once and applies `edit` to the stored list read again under the lock (`edit` may run twice; `add` refuses a list that filled up meanwhile). `writeAlarms()` is the unlocked write used inside a held section; never await `saveAlarms` or any other `locked()` call from inside one: it queues behind the item that awaits it and never starts, and the 2 s fallback lives inside `dgAlarmLock.run`, so it never arms either. All of that tab's alarm writes would stop for good. `link()`/`noteNoTicker` (`dgTickers`, `dgNoTicker`) aren't alarm data and stay unlocked. In `background.js`, `check()`'s merge section (re-check `stop()`, fresh read, drop firings whose alarm is no longer stored, switched on and of the same price, direction and repeat as at the tick's start, `R.merge`, local write, 'once' switch-off) runs under `lockOwn()`; `notify()` and `chime()` come after the release; `dgBgStatus`, `dgTickerCheck`, `dgSgSeen` stay unlocked. In `options.js`, *Clear saved data* holds it around `sync.clear` and the `local`/`session` clear. A tab's chime (`onKept`) is still started inside its section: it doesn't wait (Web Audio, or an unawaited `dg-chime` message). The banner of a tab's own firing appears once its merge has run, after its turn. `nav.js` counts them only while `navLinks` and `priceAlarms` are enabled.
- **Background check (`background.js`, flag `alarmsBackground`, off by default, needs `priceAlarms`):**
  - **What it does:** the extension's only service worker, which `importScripts('alarm-rules.js')`. While the setting and both optional permissions (notifications, Yahoo host) are on and some switched-on alarm is linked, a `chrome.alarms` timer (`dgPoll`, 1 min) fetches Yahoo's `v8/finance/spark` for the linked tickers in one request. It uses 5-minute bars: a daily bar's time is the session open, not the last trade. The last bar with a price counts. It then runs the same `R.decide` and `R.merge` as the tabs, and writes events and state to the same `dgAlarmState` and `dgAlarmEvents`, so the banner appears in DEGIRO. It also shows a system notification; a click opens the product.
  - **Links:** `S.link` writes the link `dgTickers` (sync, `{ productId: { t, cur, isin? } }`) via `R.yahooTicker`, only for products with an alarm and only when it changes. It's memoised per tab, so it adds no storage reads per frame. It's called from two places:
    - `alarm-panel.js`: from the product header's symbol, exchange name and currency, when an alarm is saved or a product page with alarms is open.
    - `alarms.js` `linkList`: from every Favourites row (also on the Alarms page, whose list stays in the DOM), using `symbolIsin`, `exchangeAbbr` (a code such as NDQ) and the `LastPrice` currency sign. The product id comes from the `symbolIsin`/`LastPrice` cells: the `exchangeAbbr` cell's `data-id` is the exchange's own id (NDQ 663, TDG 196, EAM 200), not the product's.
    - `alarms.js` `askInfo`: alarm products neither linked nor in `dgNoTicker`, in a Favourites list not on screen, say. ISIN-only links without a venue (`t: ''`, no `v: 'sg'`; an earlier build linked SG's products so) are asked about too, once per tab, so DEGIRO can name SG's venue; any other answer leaves the link as it is (`S.known`). Only while `alarmsBackground` is on (the synced setting, also on computers without the permissions: the links sync to where the check runs) and once the links and `dgNoTicker` are loaded (`S.linksReady`), it POSTs their ids (max 25, each once per tab) to DEGIRO's `/product_search/secure/v5/products/info?intAccount=&sessionId=`. It reads the session from DEGIRO's own request addresses (`performance` entries, isolated world, memory only) and calls `schedule(true)` once it has one. Error back-off is 20 s doubling to 5 min, with a timer to try again on a quiet page, and a 401/403 session isn't used again. `R.parseInfo` maps `exchangeId` to a code (`EXCHANGE_IDS`, seen live; an unknown id links by ISIN alone) and the ISO currency to the page's sign. It links with `fill: true`, so it never overwrites a link from the list or page.
  - **Alarms page Background column (`S.background(pid)` → `{ state, t, why }`, `data-dg-alarm-bg=<state>`):** the `background` column of `DG_ALARM_COLUMNS` (after `status`; `alarmColumns()` offers it only while `alarmsBackground` is on, and the Columns count ignores it otherwise). One cell per alarm: `–` when the alarm is off; `failed` and `noticker` are in `th.warn`, the others `th.muted`.
    - `ok`: "✓ ticker".
    - `pending`: "Checking with Yahoo…". Shown only while the worker ran fine in this browser in the last 5 minutes (`dgBgStatus.at` with no `err`); the page re-runs every minute.
    - `idle`: "ticker · not checked yet". The check isn't running here, for example no permissions on this computer.
    - `failed`: not found, other currency, or price doesn't match. The worker stores `why` in `dgTickerCheck`, from `R.checkLink`.
    - `noticker`: "No Yahoo ticker for <exchange>". The product was seen, but its exchange isn't in `R.yahooTicker`'s table and no ISIN is known (e.g. a future; `*` when DEGIRO names no exchange, shown as "No Yahoo ticker for this product"). `S.link` records it in `dgNoTicker` (local, `{ productId: exchange }`, `R.sanitizeNoTicker`) and drops it once the product is linked.
    - `unlinked`: "Not linked yet". The product hasn't been seen since its alarm was set (no logged-in DEGIRO tab since, or `askInfo` failed). Only the Favourites list on screen is in the DOM; `askInfo` covers the other lists. The worker checks each link once against `v8/finance/chart` (currency, plus price within 0.5–2× DEGIRO's last price) and stores the result in `dgTickerCheck` (local, key `R.linkKey` = `ticker|cur|isin`, value `{ ok, f, y, via?, why? }`; `y` is the ticker that is priced).
  - **ISIN fallback:** links from the Favourites list also carry the ISIN (`R.isinOf` of `symbolIsin`); the product header has none, and `S.link` keeps a stored one. The worker uses it when the link's own ticker doesn't pass, or its exchange has none (`t: ''`). It searches `v1/finance/search?q=<ISIN>` once, then rechecks failures at most daily, and each listing found (`R.parseSearch`, at most 3) must pass the same check. The result shows "✓ y (via ISIN)".
  - **When it skips:** products a tab priced in the last 3 minutes (`state.lastAt`) are left to the tab. A firing uses the trade's time as `firedAt`, and a price no newer than the last `firedAt` never fires, so a closed market doesn't re-fire after a restart. At merge time (storage read again), a firing from another writer at or after the worker's trade time, or within the duplicate window, wins: the worker's is dropped (no event, notification, chime or 'once' switch-off) and the stored entry stays as it is. A kept firing changes only `firedAt` on the entry as read at merge time, so `last`/`lastAt` a tab wrote while the tick's requests were out stay (`tabSeen` and the link check read them). The worker switches a kept 'once' alarm off right after storing its firing, before notifying and chiming (opening the offscreen document takes a moment, during which a tab could fire it again). "Every time" arming is kept in `chrome.storage.session`.
  - **Tabs and the worker's firings:** the worker's `firedAt` is the trade's time (about 15 minutes old, a closed market's close hours old), so a tab's 60 s window against its own clock can't catch it. A tab (`foreignWithin` in `alarms.js`) treats a foreign `firedAt` as the same firing within the duplicate window, or within 60 s of first seeing that value (its own clock; `seen`, noted from `onChanged` and from `record()`'s fresh read before the merge, since that read can return the worker's write before the event arrives). Values already stored when the tab loaded don't count as new, so a 'once' alarm switched back on (`setOn` keeps `firedAt`) fires at once. A firing the tab's merge drops is neither chimed nor switched off by the tab. "Every time" arming memory (in a tab and in the worker's `dgBgArmed`) records the stored `firedAt` it was based on (`fa`); once another writer's firing changes it (the worker's while the tab was on another page, or a tab's while the worker left the product to it), the memory starts fresh as on first sight, so a price still past the alarm stays quiet until it crosses back, whenever it is next seen. A writer's own firing sets `fa` to its new `firedAt`.
  - **Société Générale's products (SG):**
    - **What they are:** DEGIRO trades SG's turbos, factor/leverage products and certificates on its SCG venue: code `SCG` in lists, exchange id 192, header "Societe Generale OTC". The list and header show the ISIN alone where a symbol would be. Yahoo doesn't have them.
    - **Links:** `S.link` writes `{ t: '', cur, isin, v: 'sg' }` (`R.isSgVenue`). The check key is `R.linkKey` + `|sg`. Old `dgNoTicker` 'SCG' notes are dropped. A source that can't tell the venue leaves an SG link alone. DEGIRO's product details replace an ISIN-only link with an SG one.
    - **Checking a link:** the worker never sends SG links to Yahoo. It confirms them with `ValuesForWatchlist/<ISIN>` (SG's id, venue code and underlying fields, `R.parseSgMeta`, stored as `sg` in the check), and currency; no price comparison, since the ISIN on the issuer's own site names the product and a leveraged price can move far from the one DEGIRO last showed. The fields are fetched again daily, and after a refusal (4xx or the firewall's HTML page; not after a timeout or no network): a future-based product rolls. No bid (closed, halted) means no price that tick, nothing more.
    - **Prices:** `RealtimeValuesSnapshot` gives the bid, which is DEGIRO's last price for these products (verified live). It costs one request per product, at most 10 per tick, taking turns when there are more (session `dgBgSgNext`). The answer has no time: `dgSgSeen` (local, ISIN → `{ b, at }`) keeps when the bid last changed, so an unchanged bid never fires again, after a restart too.
    - **Errors:** SG's firewall answers malformed requests with an HTML "Request Rejected" (403). The worker never fakes headers to get past it. `sg()` marks a 4xx (not 408/429) or a non-JSON answer as `refused`; a 404, 410 or 204 means not found (a knocked-out or delisted product); an empty body with another OK status is a passing error, like a 5xx (never a "not found" that would unlink a confirmed product). Each product is priced in its own try, so one failing never stops the others in that tick; a failure holds only that product (session `dgBgSgHold`, by ISIN, 2, 4 … 30 minutes), and a refusal also deletes its confirmed check and holds its link check. A failed daily refresh keeps the confirmed check.
  - **Errors:** a failed link check stores nothing and holds only that link (session `dgBgHold`, by check key, 2, 4 … 30 minutes; a success clears it, and links that failed before go after the others). A whole source waits 2, 4 … 30 minutes only when its first two requests in a tick both fail, each wait on its own: Yahoo link checks (`dgBgVerifyAt`), SG link checks (`dgBgSgVerifyAt`), SG prices (`dgBgSgAt`, its counter also reset by any answer to an SG link check: confirmed, not found or another currency). Yahoo price errors make Yahoo wait 1, 2, 4… up to 30 ticks (`dgBgSkip`). One source, or one bad link, never holds up the others. `dgBgStatus` (local) feeds the status line in the settings.
  - **Settings:** `alarmsBackground` syncs across the user's computers, but permissions are granted per computer, so the check runs only where both are on. The settings switch shows that effective state. `permissions.onAdded` switches the setting on, because Chrome's prompt may close the popup. The worker never writes `false`: a computer without the permissions would otherwise switch the feature off on every other computer.
- **Alarm chime (`chime.js`, flag `alarmSound`, on by default):** Chrome on macOS shows notifications without a sound (the notifications are `silent: false`, which macOS ignores for Chrome), so the extension plays its own: two short Web Audio tones (`dgPlayChime`), no sound file. Played once per firing check, only where the firing happened and only if the merge kept it; a banner shown in another tab or again on load never chimes. Two tabs whose merges interleave (the near-simultaneous race above, only without the alarm-data lock) can both chime once.
  - **Tab:** `alarms.js` `check()` passes `chime` to `S.record`, which calls it once the merge has kept one of its firings. Chrome lets a page play sound only after a click or key in it (`navigator.userActivation.hasBeenActive`); before that the tab sends `{ type: 'dg-chime' }` to the worker, which plays it only with the `offscreen` permission (so with the background check off, a tab never clicked in stays quiet).
  - **Worker:** `chime()` after a tick's notifications (once per tick), and on `dg-chime` messages from this extension (replies `true` if played). It needs `alarmSound` and the optional `offscreen` permission, checked on its own (`SOUND`), never part of the check's `PERMS`. It opens `offscreen.html` (`AUDIO_PLAYBACK`; Chrome closes it after 30 s of silence), which plays on load; if one is still open, `createDocument` throws and the worker sends `{ type: 'dg-chime-play' }` to it. `runtime.getContexts`/`hasDocument` are newer than Chrome 111, so no existence check.
  - **Settings:** `offscreen` is requested and removed with the check's permissions (`BG_ASK`; it shows no prompt), but `bgStatus` gates on `BG_PERMS` alone. `#soundAllow` ("Allow sound with DEGIRO closed") shows while the check runs here, the sound is on and `offscreen` isn't granted (switched on before 1.25.0); it is checked from `bgStatus`, never from the status line (`bgLine`). The test notification also asks the worker for the chime, and plays it in the popup if the worker can't.
- **Alarms page route:** `#/favourites?dg=alarms`. Inside `#/favourites…` DEGIRO keeps the query sticky (it merges the old query back into every move), so a click on one of DEGIRO's favourites links from the Alarms page is intercepted and sent to `href` + `dg=` (an empty value), which DEGIRO then drops.
- **Alarm badges on the chart (`alarm-lines.js`, flag `alarmLines`, needs `priceAlarms`):** `alarms.js` writes only the open product's id and its switched-on alarms' price and direction to `data-dg-alarm-lines` on `<html>` (e.g. `{"id":123,"l":[{"p":20,"d":"above"}]}`); the page can read and write it, so `alarm-lines.js` validates it strictly and ignores the whole value on any bad entry. Gold HTML badges at the price on the main chart's right edge, ▲/▼ pinned when out of range; no plot lines.
- **Product header:** period change, header spread, and ex-dividend date share a wrapping `[data-dg-header]` container after DEGIRO's price line, ordered by `data-dg-rank`. Each feature removes only its own item and removes the container when empty.
- **DOM robustness:** prefer language-independent hooks such as `data-field` and `data-name`, with localized label text as fallback. Parse both `1.234,56` and `1,234.56`; reapply after DEGIRO rerenders through the scheduler. Copy DEGIRO's palette; read its fonts from the page rather than hard-coding them (`fontFamilyOf` / `chartFont` in `common.js` take the computed font of the nearest DEGIRO text; the Roboto stack is only the fallback).
